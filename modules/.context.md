
# Protocol-7 Modules Directory Context

## Purpose
This directory contains the core functionality of Protocol-7, organized as a collection of reusable code libraries (modules) that implement various aspects of the system. These modules are loaded by zenki based on their specific requirements, providing a modular and extensible architecture.

## Module Organization
- **Hierarchical Namespace**: Modules follow a dot-notation namespace convention (e.g., `io.unix`, `crypt.C25519`)
- **Directory Structure**: The physical organization mirrors the logical namespaces with nested directories
- **Specialized Modules**: Zenki-specific modules that implement functionality for particular agents
- **Core System Modules**: Fundamental components used by most zenki

## Special Module Naming Conventions
- **\*.cmd.\***: Command handler modules that define commands a zenka can execute
- **\*.cli.\***: Command line interface modules for user interaction
- **\*.pre_init**: Code executed before the main initialization phase
- **\*.init_code**: Initialization code executed during zenka startup
- **\*.post_init**: Code executed after the main initialization completes

## Module Loading Order
- Modules are loaded in order of name length, with shortest names first
- This ordering is visible in the startup sequence (e.g., `net` before `cube` before `auth` before `io.unix`)
- The `base` module is typically loaded first as it provides foundational functionality
- Dependencies are managed through this implicit loading order in addition to explicit declaration

## Core Module Categories
- **auth**: Authentication and permission validation systems
- **net**: Network communication primitives and abstractions
- **protocol**: Message protocol implementation and routing
- **io.unix**: Unix-specific input/output operations
- **io.ip**: IP-based network communication
- **crypt**: Cryptographic functions and security protocols
- **base**: Low-level functionality used throughout the system

## Specialized Module Categories
- **Zenka-specific modules**: Modules named after zenki providing their core functionality
- **Data Processing**: Modules for specific data formats and transformations
- **External Integration**: Modules for connecting with external systems
- **User Interface**: Modules supporting various UI paradigms
- **System Access**: Modules for hardware and operating system interactions

## Module Loading Mechanism
- Modules are loaded via the `[load_modules:<modules.load>]` directive in zenka start files
- Dependencies are managed through explicit loading order in the modules.load parameter
- Common module patterns are shared across related zenki
- Some zenki use specialized protocol variants (e.g., `protocol.protocol-7`)

## Module Implementation
- Modules are primarily implemented in Perl (matching the 82.4% of repository)
- Performance-critical components may have C implementations
- Modules expose a consistent interface pattern to the zenki that load them
- Code follows the project's harmonic naming and organization principles

## Common Module Dependencies
The most frequently loaded module combinations based on zenki configurations are:
- Basic zenki: `auth net protocol io.unix` plus zenka-specific module
- Network-enabled zenki: `auth net protocol io.unix io.ip` plus zenka-specific module
- Cryptographic zenki: Include `crypt.C25519` in their dependencies
- Configuration-supporting zenki: Include modules like `set-up` for structured configuration management

## Development Module
- The `devmod` module provides development capabilities for debugging, testing, and system introspection
- It is typically commented out in production configurations with `## devmod` comments
- These comments are designed to be easily uncommented when development features are needed
- The parser ignores these module references when they're commented out
- Additionally, sending `SIG53` to a running zenka process enables the devmod module during runtime
- When enabled via signal, the system warns about devmod activation both on console and in logs

## Relation to Other Components
- Modules are loaded by the Protocol-7 interpreter during zenka initialization
- Configuration files specify which modules each zenka requires
- The bin/ directory contains tools that may utilize these modules
- Multiple zenki may share common modules while maintaining separation
