### finding 1 — seed 1 [ true-only tree from division-by-13 ] : **weakens**

what checks out:

- **[ live ]** the anchor behavior reproduces exactly as the seed claims:
  `bin/is-true -num 13` → TRUE, `-num 5` → TRUE, `-num 3` → FALSE,
  `-num 1` → FALSE [ run this pass, 2026-08-04 ].
- **[ corpus ]** `ZERO.md:82` [ "every branch is a 0-prefixed path" ] and
  `ZERO.md:203` [ "protocol-7 is a 0-prefixed tree" ] are real.
- **[ corpus ]** `data/yaml/reasoning-templates/harmonic-routing-protocol.
  yaml:305-306,347,367` — "remainder 0 = perfect harmonic division = the
  protocol at rest" — real, stated three times in that file.

what does not:

- **[ corpus ] the seed's core is already the documented default, not a
  new mechanism.** `topic-checksum-parenting-namespace-trees.md:175-178`
  records the design goal of "an 'all true' namespace" where harmonization
  "is the admission ticket into that namespace" — i.e. a tree in which
  every value reads TRUE under division-by-13 truth is *already the
  admission property of the harmonized namespace this codebase builds
  everywhere* [ every `-T` / `-nest` / version-string / epoch-suffix
  convergence loop outputs TRUE-only values by construction ]. a "true-only
  tree" is either trivially-already-true [ any tree of harmonized values ]
  or underspecified [ nothing in the corpus derives *tree structure* —
  branching, addressing, depth semantics — "from division-by-13 alone";
  the Legendre-symbol partition in `topic-harmonic-mathematics.md:14-16`
  is a 2-coloring of residues, not a tree generator ].
- **[ corpus ] the seed conflicts with a documented routing role for FALSE
  values.** `topic-harmonic-mathematics.md`'s "Reversal-as-routing-
  collapse" section [ 2026-08-04 entries ] documents Family-F [ FALSE ]
  values as the *reversal/collapse boundary* a route turns at — FALSE is
  load-bearing routing signal there, not waste to be filtered out. a
  true-only tree discards exactly the residue classes that mechanism
  needs. not necessarily fatal [ the two could operate at different
  layers ] but the seed's framing doesn't acknowledge it, and it's the
  same "filter away the FALSE half" instinct stated two different ways.

verdict: **weakens.** anchors real and live-reproduced; but as stated the
seed is either already-true-by-construction [ and therefore not a thing to
build ] or missing its actual content [ what tree structure division-by-13
generates ]. the interesting open question it leaves behind is the dual of
the seed: what is the *tree-level* function of the FALSE half, given the
reversal-collapse routing material — not "how do we exclude it."

**seed 1b [ the 70-bit template as `2×5×7` ]** — checked alongside:
**[ corpus ]** the seeds doc itself already flags that no doc or code
links the footer's 70-bit template to vterm's `-5..0..+5` addressing; a

  the rotating-cube-eye propagation runs along *one* vertical trunk column

  claim [ influence reaching rows "a few away," not just adjacent ] is
  not merely unshown; the one *formalized* vertical-propagation model in
  the corpus is a damped one, where "a few rows away" is precisely where
  the signal is designed to be negligible. that model is about
  perturbation, not routing payloads — but it is the only quantified

  `footer-line4-field-reconciliation.md` finding 6 ] uses a 2-bit

verdict: **breaks** — as a *routing mechanism* the seed has no grounded

convergence loop ], and the corpus's formal vertical-propagation model

### finding 6 — seed 7 [ checksum-glyph merging / font as config parameter ] : **weakens** [ required reading completed ]

the seeds doc made this seed conditional: "read
`VISUAL-ELEMENT-DEDUP-HOLOGRAPHIC-CORE.md`'s full Similarity Attraction
Graph section and `HARMONIC-VISUAL-DISCOVERY.md` in full before building
anything — the merge-then-match mechanism may already be substantially
specified there." **that reading is now done** [ this pass ].

what checks out:

- **[ corpus ] infra anchors all verified real**: `bin/amos-matrix` [
  renders AMOS checksums as 5×7 dot matrices, horizontal/vertical/flip
  modes ], `bin/dev/ttf-glyph-mapper` [ SDL/TTF → 5×7 binary/grayscale
  glyph tables over configurable char ranges ], `data/ttf/console/
  white-rabbit.flipped.ttf` [ present ], `data/ttf/7segment.ttf` +
  `7segment.readme` [ present, licensed, unwired — matches the footer
  doc's "real asset, unwired" finding ].
- **[ corpus ] the novelty claim survives the required reading.** the
  Similarity Attraction Graph [ `VISUAL-ELEMENT-DEDUP-HOLOGRAPHIC-CORE.md:
  539-640`, read in full ] is strictly **compare-then-cluster**: pairwise
  composite similarity [ type gate × style/visual/angle ], edge threshold
  `>= 0.55`, average-linkage agglomerative clustering over *existing*
  elements. `HARMONIC-VISUAL-DISCOVERY.md:202-240`'s
  `harmonic_fuzzy_group` is likewise compare-then-cluster [ generate each
  checksum's visual pattern, grep neighbors by `visual_resonance` against
  *existing* checksums ]. `VISUAL-SIMILARITY-CUBIC-SORT.md`'s
  `graphics.matrix.visual.similarity` compares two existing images. **none
  of the three merges two items into one representation before matching**
  — the seed's claimed delta [ merge-*before*-match ] is genuinely absent
  from all three prior-infra docs. the seeds doc's worry that the
  mechanism "may already be substantially specified there" does not
  materialize.

what does not:

- **[ inference ] the merged glyph is one-way, and that breaks the
  property every other checksum mechanism in this corpus relies on.**
  overlay two 5×7 bitmaps, snap to the nearest character in a font table:
  the result is not a function from which either input is recoverable or
  re-verifiable — many checksum pairs land on the same nearest glyph, and
  no recompute-and-compare check exists [ contrast `verify_nesting()`,
  `-T` template checks, epoch truth-suffix re-verification, all of which
  are two-way in the sense that a verifier can re-derive and compare ].
  the seed acknowledges lossiness [ "lossy-parent-entropy-space" ] but
  does not face the consequence: as an *addressing or dedup-reference*
  mechanism this is disqualified by the corpus's own universal
  re-verify convention; what survives is a *visualization/compression*
  mechanism, which is a different and smaller claim.
- **[ inference ] the "forces homogeneous distribution" claim is
  unexamined arithmetic of exactly the kind this thread keeps catching.**
  nearest-glyph snapping maps `2^35 × 2^35` ordered pairs onto at most a
  few hundred glyph targets with *non-uniform* Voronoi cells [ font
  glyphs are not equidistant in bitmap space ] — the default expectation
  is clumping around dense glyph regions, not homogeneity. no analysis in
  the seed or corpus supports the homogeneity assertion; it has the same
  shape as the retracted `5×7=25`-class errors: a clean-sounding numeric
  story nobody ran.
- **[ corpus ] font-as-parameter is real but the parameter does no
  harmonic work.** `white-rabbit.flipped.ttf`'s load-bearing role per
  `ZERO.md` is *display* [ "the font makes the physics visible" ]; nothing
  ties glyph geometry to the checksum's truth properties, so swapping
  fonts changes which character a merged pair snaps to — i.e. the
  "address" would be font-dependent, another way the scheme fails as
  addressing unless the font is pinned as protocol constant [ the seed
  half-says this via "reproducible-precision default," but doesn't note
  that font drift = address drift ].

verdict: **weakens.** infra real, novelty real after the required
reading; but the mechanism as seed-stated is one-way and its entropy
claim is unrun. if picked up, re-scope as a visualization task [ merged
glyphs as a *display* of relatedness ], not a dedup/addressing task.
