## task: slim scan-state.yaml to orchestration-only state

### motivation

`scan-state.yaml` currently persists `<jobsite.tasks>` — a full in-memory
map of job stages, scores, assertions, repair flags, etc. after the
status-dir restructure, all of this data is already durably stored in the
per-job YAML files under `jobs/<status>/`. persisting it again in
scan-state creates a second source of truth that can diverge on restart.

the fix: remove `tasks` from scan-state entirely. on restart, `state.load`
restores only orchestration fields; `job.load_all` reconstructs all job
data from the filesystem.

---

### what scan-state.yaml should contain after this change

```yaml
---
cycle: idle
last_scan: 1780179337
sync_last_ntime: 3TBNBF6YLGCNKCQ
pending_count: 0
```

only these four fields. nothing about individual jobs.

---

### what moves to the filesystem (if needed at all)

any scan-state metadata that needs to outlive a restart and isn't already
in a job YAML goes into a dedicated subdirectory of the checksum store or
the jobsite var dir. for example, if we ever need to persist the
`assess_queue` (ordered list of job IDs waiting for dispatch), that can go
into:

```
/var/protocol-7/jobsite/scan-state/assess-queue/<position>.<id>
```

(files named by position + id, sorted lexicographically = ordered queue).
for now no additional subdirs are needed — the four fields above are enough.

---

### changes to jobsite.state.load

remove the `tasks` restore block. keep only:

```perl
<jobsite.last_scan>              = $saved->{'last_scan'}       // 0;
<jobsite.pending_count>          = $saved->{'pending_count'}   // 0;
<jobsite.sync.last_server_ntime> = $saved->{'sync_last_ntime'} // ''
    if length( $saved->{'sync_last_ntime'} // '' );

## cycle: reset scanning/assessing to idle ##
my $cycle = $saved->{'cycle'} // 'idle';
$cycle = 'idle' if $cycle =~ m{^(?:scanning|assessing)$};
<jobsite.cycle> = $cycle;
```

remove the in-flight task stage reset loop (lines 30–41) — no longer
needed since tasks are not persisted.

keep the store.yaml migration block (lines 43–82) until confirmed gone.

---

### changes to jobsite.state.persist

currently serializes `<jobsite.tasks>` into the YAML. replace with:

```perl
my $state = {
    'cycle'           => <jobsite.cycle>                // 'idle',
    'last_scan'       => <jobsite.last_scan>            // 0,
    'pending_count'   => <jobsite.pending_count>        // 0,
    'sync_last_ntime' => <jobsite.sync.last_server_ntime> // '',
};

my $yaml  = YAML::XS::Dump($state);
my $wrote = <[file.zenka_dir.write]>->( 'scan-state.yaml', \$yaml, '>', 0640 );
```

---

### changes to jobsite.init_code

after `state.load`, add:

```perl
## rebuild job index and in-memory task map from filesystem ##
<[jobsite.job.index.build]>;
<[jobsite.job.load_all]>;
```

`job.load_all` already scans the status dirs and populates `<jobsite.tasks>`
from the job YAML files — this replaces the scan-state restore path.

---

### changes to jobsite.job.load_all

currently populates `<jobsite.tasks>` from job YAMLs. ensure it sets these
fields per job from the YAML content:

```perl
<jobsite.tasks>->{$id} = {
    'status'           => $job->{'status'}        // 'new',
    'stage'            => $job->{'stage'}         // '',
    'score'            => $job->{'score'}         // '',
    'repair_attempted' => $job->{'repair_attempted'} // FALSE,
    'repair_failed'    => $job->{'repair_failed'}    // FALSE,
};
```

this makes `<jobsite.tasks>` a derived view of the filesystem, not a
separate persistent store.

---

### backward compat

existing `scan-state.yaml` files on disk may still have a `tasks:` key.
`state.load` should simply ignore it — do not read it, do not error on it.
YAML::XS::Load will parse it into `$saved->{'tasks'}` but we just never
access that key.
