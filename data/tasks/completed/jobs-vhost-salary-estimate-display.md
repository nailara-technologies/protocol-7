## task: show Stepstone salary estimate on jobs.vhost

### read first

- `data/ai-mem/kimi/coding-style.md` and `data/ai-mem/kimi/MEMORY.md`
- `data/web-root/vhosts/jobs.vhost/index.html` — the single file for this
  task (frontend only, plain JS/CSS/HTML, no P7 module conventions apply
  here beyond general code quality)

### context

`src/site-yaml.stepstone.job` was just extended to extract
`salary_estimate_min`/`salary_estimate_max` (integers, annual gross EUR)
from Stepstone job pages, and store them on the job record when present
(both keys are simply absent when Stepstone shows no estimate — never
`0`/`null`). This already flows unchanged through the live sync path
(`src/plugin.web.jobs.data` spreads the full stored job hash,
`%{ $jobs->{$job_id} }`, into the JSON it serves) — **no backend changes
are needed**, the field is already reaching the browser today, just
unused by the frontend.

Your job is purely frontend: render it wherever it's useful, guarded on
presence (`j.salary_estimate_min != null` — never assume both keys exist
just because one does, but in practice the backend always sets both or
neither).

---

### 1. job card (`renderCard`, around line 1006 of index.html)

Add the range to `.card-meta` (city/company/industry row), around line
1090-1094. Something like a new `<span class="salary">` shown only when
present:

```js
${j.salary_estimate_min != null && j.salary_estimate_max != null
  ? `<span class="salary">€${Number(j.salary_estimate_min).toLocaleString('de-DE')}–${Number(j.salary_estimate_max).toLocaleString('de-DE')}</span>`
  : ''}
```

Add a `.card-meta .salary` CSS rule near the existing `.card-meta .company`
/`.card-meta .city` rules (around line 352-354) — pick a color consistent
with the existing muted meta-row palette, don't invent a new accent color
family for this.

### 2. CSV export (`exportCSV`, around line 1781)

Add a `Gehaltsschätzung` column. Follow the existing `cols`/row-building
pattern exactly (line 1785-1804) — one more entry in `cols`, one more
value in the row array, formatted as `"53000-77000"` or empty string when
absent (do not write "n/a" or similar placeholder text — empty is
correct here, matching how other optional fields like `note` are handled
in that same row).

### 3. print report (`showPrintTable`, around line 1820)

Add the range to the per-job detail block (around line 1851-1854, the
`company · city · industry · stage · date` meta line) — append
` · €min–max` when present, same inline style as the other `·`-joined
meta pieces. Do not add it to the overview table (line 1829, the compact
`Nr/Datum/Unternehmen/Position/Ort/Score/Status` table) — that table is
intentionally compact, adding a column there would crowd it.

---

### testing

Since this is a browser file, sanity-check by hand: open
`data/web-root/vhosts/jobs.vhost/index.html` (or wherever it's deployed
locally) and confirm:
- a job with both `salary_estimate_min`/`_max` set shows the range on its
  card, in the CSV export, and in the print report detail line
- a job with neither key set shows no salary anywhere and produces no
  JS console errors (`j.salary_estimate_min` is simply `undefined` on
  those records, not `null` — `!= null` in JS is true for `undefined` too,
  so the guard above already covers both cases correctly)
- existing card layout / CSV columns / print report for jobs without an
  estimate are pixel-for-pixel unchanged (no stray separators, no empty
  `<span>` tags)

If no local jobs.vhost data has real salary estimates yet in your test
environment, you can temporarily inject fake values in the browser
console (`jobs['<some id>'].salary_estimate_min = 53000; jobs['<some
id>'].salary_estimate_max = 77000; render();` or however the existing
`jobs` object / `render()` call is named in this file) to verify the
rendering, then revert before finishing — don't leave test data in the
committed file.
