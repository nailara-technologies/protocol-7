# X-11 connection pool: replay-registration fix + query reroute + health-oracle ping

## context, read first

`src/X-11.*` — the X-11 zenka holds a single `X11::Protocol` connection
in `<X-11.obj>` (a P7 data-path expression, expands to `$data{'X-11'}{'obj'}`).
Under WSLg/Weston this connection can silently stall mid-round-trip (compositor
issue, not a protocol-7 bug — see `data/ai-mem/claude/topic-x11-protocol-hardening.md`
for the full incident writeup, read it before starting). Full design already
converged in that memory file's "Blocking-call hardening" section — this task
implements it. Don't re-derive the design, follow it.

Full design doc: `data/ai-mem/claude/topic-x11-protocol-hardening.md`

## p7 conventions — read before writing any code

- module files have NO `sub {}` wrapper — the filename IS the subroutine. code
  starts right after the `## [:< ##` header + `# name = ...` / `# descr = ...`
  comment block.
- call other modules with `<[module.name]>` (implicit `->()`, no args) or
  `<[module.name]>->( $arg )` (explicit `->()` only when passing args).
- data-hash access: `<a.b.c>` expands to `$data{a}{b}{c}`. use this for all
  config/state, never invent a raw `%data` access.
- logging: use `<[base.logs]>->( $level, $fmt, @args )` (printf-style, level
  0=error..N=verbose), NOT `<[base.log]>->( $level, $string )` unless it's a
  single already-formatted message with no interpolation args — check
  existing `X-11.*` modules for the exact split, they use both correctly.
- constants: `TRUE => 5`, `FALSE => 0`, `UNKNOWN => 2` — never bare `1`/`0`
  for these semantics.
- every new/modified module needs an entry in `cfg/zenki/X-11/subroutine.white-list`
  (new modules only, alphabetical-ish, follow existing ordering nearby) AND
  `src/base.list.subroutines` (same list, different file, both must match
  or signature verification fails).
- comments: lowercase, `[ word ]` brackets not `( word )`. see any existing
  `X-11.*` module for the narrative style.
- do NOT hand-edit `data/md/documentation/module-dependency-graph.asc` — it's
  regenerated by `bin/dev/dep-graph`. run it after your changes, let it update
  the file, and stage the result as-is.
- do NOT write AMOS7 signature footers (the `#,,,...` / `#XXXX...` /
  `#\\\|...` / `#\[7]...` block at the end of every file) — those are added by
  the human's signing pass after your changes land. Leave new files without
  one; don't fake it.
- do NOT run `git add`, `git commit`, or touch version files
  (`cfg/protocol-7.src-ver`, `read-me/md/README.md`,
  `read-me/project-identity/source-code-versions.md`) — the human handles
  staging, signing, and commits.

## files to read for existing patterns

- `src/X-11.reconnect` — current reconnect logic (re-dial + exponential
  backoff). You're adding a replay step to this.
- `src/X-11.connect_X11` — how the primary connection is dialed today
  (`X11::Protocol->new(...)`, retry loop, `X-11.WM->new(...)`). Your standby
  dial logic should mirror the connection-establishment part of this but
  must NOT call `<[base.exit]>`/`kill` on failure — a failed standby dial is
  not fatal to the zenka, just means no pool coverage until the next attempt.
- `src/X-11.job.finalize_server` — line ~111 `RRSelectInput`, line ~247
  `<[X-11.grab_key]>` — the two per-connection registrations that currently
  get silently dropped on reconnect. There may be others; grep `X-11.*` for
  any other `SelectInput`/`ChangeWindowAttributes`/`Grab*` calls on
  `<X-11.obj>` and include them in the replay function too.
- `src/X-11.grab_key` — trivial, shows the `GrabKey` call shape.
- `src/base.exec.with_timeout` — the `select()`-with-deadline pattern to
  reuse (NOT the open3/subprocess parts, just the `select()` + deadline
  loop shape) for bounding a socket read without blocking the event loop.
  The X11 connection's fh is `$X->{connection}->fh` (or `<X-11.obj>->{connection}->fh`
  in P7 dot-path — verify this resolves correctly, `X11::Protocol::Connection`
  and `X11::Protocol::Connection::Socket` in `X11::Protocol`'s own source have
  the `fh` accessor if you need to check).
- `src/base.s_read` — non-blocking sysread primitive, same one
  `base.exec.with_timeout` uses. Reuse it for the socket-read-with-timeout too.
- `src/X-11.WM.update`, `src/X-11.get_window_ids` — two call sites
  that do direct `<X-11.obj>->GetProperty(...)` / `QueryTree` / etc. reads;
  wire the query-reroute wrapper into at least these two as the worked
  example (don't need to convert every caller in this pass — note remaining
  call sites you didn't touch in your summary at the end).

## what to build

### 1. replay-registration function (fixes an existing bug, needed regardless of the pool)

New module, e.g. `src/X-11.reconnect.replay_registrations` — takes no
args (operates on whatever `<X-11.obj>` currently points to), re-issues:
- `RRSelectInput` (as done in `X-11.job.finalize_server` line ~111)
- `<[X-11.grab_key]>` (as called in `X-11.job.finalize_server` line ~247 —
  check what args it's called with there, some deployments may register
  multiple keys/modifiers, check for a loop or list of registered hotkeys
  in `X-11.job.finalize_server` or its config)
- anything else per-connection you find via the grep mentioned above

Wire this into `src/X-11.reconnect` — call it right after
`<X-11.obj>->init(...)` succeeds, before `<[X-11.init_display_states]>`.

### 2. standby connection pool

New modules under `X-11.pool.*`:

- `X-11.pool.dial_standby` — dial a second `X11::Protocol` connection
  (mirror `X-11.connect_X11`'s connection-establishment logic, single
  attempt or short bounded retry, NOT the indefinite host-mode retry loop),
  store it at `<X-11.obj.standby>`, then call
  `<[X-11.reconnect.replay_registrations]>` against it (you'll need to
  parameterize that function to accept a target connection object instead
  of always operating on `<X-11.obj>` — do this refactor, it's needed for
  both callers). On failure, log via `<[base.logs]>` and leave
  `<X-11.obj.standby>` undef — don't retry synchronously in a blocking loop,
  schedule a retry via `<[base.event.add_timer]>` (check its signature in
  `src/base.event.add_timer` or any existing caller like
  `X-11.update_X11_WM` for the exact args) a reasonable delay out (e.g. 5s),
  don't retry more than a few times before backing off further.

- `X-11.pool.ping_standby` — fire `GetInputFocus` (or similar cheap no-op)
  on `<X-11.obj.standby>` bounded by the `select()`-with-deadline pattern
  from item 1. Returns TRUE/FALSE (healthy/not), never blocks past the
  deadline (short, ~1-2s).

- `X-11.pool.query` — generic wrapper: `<[X-11.pool.query]>->( $method_name, @args )`.
  Calls `$method_name` on `<X-11.obj>` bounded by the same select()-timeout
  pattern (2-3s default, make it a param or config value
  `X-11.pool.query_timeout`). On timeout/failure:
  1. call `<[X-11.pool.ping_standby]>`
  2. if standby healthy: retry the same `$method_name(@args)` call on
     `<X-11.obj.standby>`, log at level 1 that a reroute happened, return
     its result
  3. if standby also fails/absent: log at level 0 that this looks systemic
     (matches the compositor-level failure class in the design doc), return
     undef — do NOT attempt promotion or further retries here, that's a
     separate concern (item 3)

  Only use this for read-only X11 calls (`GetProperty`, `QueryTree`,
  `GetWindowAttributes`, `GetGeometry`, `TranslateCoordinates`,
  `GetInputFocus`) — do not route `GrabKey`/`SelectInput`/anything mutating
  through this, those must stay pinned to whichever connection currently
  owns the registered state. Say so in a comment at the top of the module.

- `X-11.pool.promote_standby` — swap `<X-11.obj.standby>` into `<X-11.obj>`
  (save the old primary temporarily, don't just overwrite-and-lose-it —
  close the old primary's connection cleanly if `X11::Protocol` exposes a
  disconnect/close method, check its source or existing usage for how P7
  tears down connections elsewhere, e.g. does anything call
  `->{connection}->close` or similar on zenka shutdown?), clear
  `<X-11.obj.standby>`, then schedule
  `<[X-11.pool.dial_standby]>` again via a short timer (don't call it
  synchronously inline — keep this non-blocking) to refill the pool.

  Call `X-11.pool.promote_standby` from `X-11.pool.query` in the case-3
  path above only if you judge it should trigger promotion — reread the
  design doc's distinction between "per-request reroute" (no promotion) and
  "full promotion" (only for a stuck *mutating* call) before deciding
  whether `query`'s systemic-failure branch should call promote or not. If
  unsure, leave promotion uncalled from `query` and only wire it as a
  standalone module other code can call explicitly when a mutating call
  hangs — flag this decision explicitly in your summary either way.
