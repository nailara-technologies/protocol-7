# dep-graph semantic embeddings — task

## context

track: [[EMBEDDING-INFRASTRUCTURE-TRACK]], [[FASTTEXT-MEMORY-PIPELINE]]
design: [[INDEX-FASTTEXT-SOURCECODE-EMBEDDINGS]] (relational perspectives bullet)
data: data/md/documentation/module-dependency-graph.asc (generated by bin/dev/dep-graph)
source: duck.ai design conversation 2026-07-29 (prompts 61–63)

greenfield: nothing currently combines the module dependency graph with
embeddings. the .asc adjacency list is already in word-neighbor format
(`source : callee ...`), module names are dot-separated semantic trees
(`base.utf8.clean_str`), and each module name IS its filepath under
modules/ — no registry, no lookup table. training an embedding model on
the dep-graph gives the coding zenka semantic navigation: query neighbors
→ convert to filepaths → parallel-load only relevant modules instead of
blind recursive file discovery.

existing adjacent capability: coding zenka already has module_deps /
dep_graph tools (modules/coding.tools.definitions) — those give exact
adjacency; embeddings add ranked semantic NEIGHBORHOODS and cross-module
pattern discovery.

## phase 1 — corpus + model

### task 1.1 — dep-graph corpus assembler
```
## dispatch + prompt
new corpus assembler for the fasttext pipeline (fits phase 1 of
[[FASTTEXT-MEMORY-PIPELINE]]): transform module-dependency-graph.asc
into skipgram training lines — strip ' : ', one line per module with
its callees; optionally add reverse edges (callee → callers) as
separate lines weighted lower. regenerate automatically when the .asc
changes (hook into dep-graph regeneration).
output: data/training/codebase-depgraph.txt
```

### task 1.2 — train + verify
```
## dispatch + prompt
train: fasttext skipgram -input data/training/codebase-depgraph.txt
  -output data/embeddings/codebase-depgraph -epoch 100 -dim 300
  -minn 3 -maxn 6 -wordNgrams 2
verify with spot queries: nearest neighbors of 'base.log' should be its
callees + logging-adjacent modules; 'data.get.resolve_virtual' should
cluster with the other resolve_* and classify_* modules. record results.
```

## phase 2 — coding zenka integration

### task 2.1 — semantic context loader
```
## dispatch + prompt
new module coding.context.semantic-load: given a target module name,
query the dep-graph embedding for N nearest neighbors, convert names
directly to modules/<name> filepaths, parallel-load contents, return a
context bundle (primary, neighbors, bytes). expose as a coding zenka
tool alongside module_deps — model decides when semantic neighborhood
beats exact adjacency.
reference perl sketch: conversation transcript prompt 63
(Protocol7::SemanticLoader) — adapt to module conventions.
```

### task 2.2 — measure the difference
```
## dispatch + prompt
run one real coding task twice (e.g. 'optimize data.get.resolve_plugin'):
once with existing tools, once with semantic-load. measure: files
loaded, context tokens used, cross-module opportunities found, time to
first proposal. write results to data/md/code-reviews/ — this is the
evidence base for whether embeddings earn a permanent slot.
```

## phase 3 — evolution awareness

### task 3.1 — embedding drift across retraining
```
## dispatch + prompt
keep the previous model file on retrain; add a compare step that reports
semantic drift (which modules moved clusters, which clusters formed/
dissolved) as an architecture-evolution signal into the forensics
channel. embedding-space diff = visible code-structure momentum.
```

## notes

- minn/maxn subwords are what make dot-separated names work: shared
  prefixes (base.*, data.get.*) get shared subword vectors.
- the filesystem-as-index property is the elegance: no indirection
  layer. keep it that way.
