## gaps

- **no precise data structure** for the loves-it tree node itself beyond
  "groups of groups + pool" — no schema for what a loves-it reference
  record contains (who/what/when), how the proximity metric is computed
  for clustering (which metric space — BMW384 coordinates? semantic?), or
  the tree's storage layout (beyond the generic `valued.*` N+f note).
- **detection matrix is undefined operationally**: no algorithm, no
  fingerprint format, no update rule beyond "compressed essence fingerprint
  / more precise than full representation / self-updating". no code
  implements it; only analogies (kitten composite filter, roadmap-as-matrix).
- **resource pool has no defined mechanics**: no ledger schema, no
  contribution-measurement definition, no overflow/disbursement algorithm,
  no interaction with NRT.NRD token plumbing specified
  (LOVES_IT_RESOURCE_ALLOCATION.md is the closest, and its Week 1-5
  roadmap items are all unchecked).
- **formation mechanics are one sentence**: "usage event → reference
  count++" (roadmap 4b.4) — no event taxonomy, no decay rule (only the
  love-field decay constant δ in LOVE-AS-AMPLIFICATION.md:236 as
  intuition, and "reference count drop = fade" in roadmap:363 without a
  mechanism).
- **proximity clustering unspecified**: the proximity metric that
  "clusters automatically" is never named for the loves-it layer (BMW384
  coordinate proximity exists in the address-space layer, topics 4.x, and

- **current vs overall love separation** (LOVE-AS-AMPLIFICATION.md:106-155)
