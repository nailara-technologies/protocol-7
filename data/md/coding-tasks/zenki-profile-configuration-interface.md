# Zenki Profile Configuration Interface

## Overview

Extend the v7 zenka startup system with a dynamic profile mechanism that uses
existing P7 architectural features: zenka subnames for instance identity, and
the currently unused `system.args` command interface for profile and zenka
management. The static `start-set-up.base` profile remains unchanged as a
stable fallback — the new system adds around it rather than replacing it.

## Current State

- `cfg/zenki/v7/zenka.v7` selects the startup profile via:
  `load.start_setup = base` → loads `cfg/zenki/v7/start-set-up.base`
- The comment already anticipates alternatives: `## [ additional : local-models + remote-server ]`
- `[v7.call_cmd:<system.args>]` is present in `v7/start` but intentionally
  unused — the command space was too open to commit to a partial design
- Zenka subname mechanism (`zenka-name[subname]`) is fully implemented and
  already factors into socket path and network listen address calculation,
  enabling concurrent instances without conflict

## Core Architecture

### Two Orthogonal Dimensions

**1. Subname → profile identity** (which v7 instance / which profile to start)

```
Protocol-7 v7                    ## auto-resolve: hostname → local → base
Protocol-7 v7[setup]             ## explicit first-run wizard
Protocol-7 v7[minimal]           ## directly loads start-set-up.minimal
Protocol-7 v7[DESKTOP-FP4OP26]   ## directly loads start-set-up.DESKTOP-FP4OP26
Protocol-7 v7[server]            ## loads start-set-up.server
```

Because the subname feeds into socket path and listen address, `v7[desktop]`
and `v7[server]` are fully isolated concurrent instances by design — no extra
machinery needed.

**2. system.args → commands** (manage configuration and state of a starting
or running instance — see command taxonomy below)

### Profile Resolution (no subname)

When v7 is started without a subname, `v7.resolve_startup_profile` determines
which profile to load:

```
1. start-set-up.<hostname>    exists → use it   [ normal operation ]
2. start-set-up.local         exists → use it   [ manual override ]
3. start-set-up.setup         → first-run wizard [ no host profile yet ]
4. start-set-up.base          → last-resort fallback
```

### Profile Files

```
cfg/zenki/v7/start-set-up.base          ## unchanged stable reference
cfg/zenki/v7/start-set-up.setup         ## first-run wizard profile
cfg/zenki/v7/start-set-up.minimal       ## preset: core only
cfg/zenki/v7/start-set-up.development   ## preset: + coding, models
cfg/zenki/v7/start-set-up.<hostname>    ## generated by setup wizard
cfg/zenki/v7/start-set-up.local         ## manual local override
```

Profile inheritance: host profiles should extend base via include/override
rather than duplicate it — e.g. `zenki.enabled += httpd` or
`zenki.disabled -= coding`. Include semantics need to be defined.

## system.args Command Taxonomy

Designing the command interface now alongside the profile system avoids
ad-hoc retrofitting later. The space divides naturally into four categories:

### Profile Management (persistent — writes config)

| Command | Effect |
|---------|--------|
| `set-profile:<name>` | Permanently select startup profile for next boot |
| `save-profile:<name>` | Save current running configuration as a named profile |
| `list-profiles` | Show available `start-set-up.*` files with summary |
| `show-profile:<name>` | Print a profile's zenki list and config |
| `delete-profile:<name>` | Remove a generated profile file |

### Zenka Management (affects running instance)

| Command | Effect |
|---------|--------|
| `start:<zenka>` | Start a zenka in the running instance |
| `stop:<zenka>` | Stop a running zenka |
| `restart:<zenka>` | Restart a running zenka |
| `enable:<zenka>` | Add zenka to current profile (persists) |
| `disable:<zenka>` | Remove zenka from current profile (persists) |
| `status` | Show running zenki, states, uptime |

[ could support both fornats ':' and '=' as command and parameter seperator ]

### Setup and Configuration

| Command | Effect |
|---------|--------|
| `configure` | Run setup wizard (equivalent to `v7[setup]` for running system) |
| `detect-hardware` | Re-run hardware detection, suggest profile adjustments |
| `reconfigure:<zenka>` | Reconfigure a specific zenka's options |

### Introspection (read-only, no side effects)

| Command | Effect |
|---------|--------|
| `list-zenki` | All discoverable zenki with metadata and requirements |
| `show-hardware` | Current hardware capabilities and detection results |
| `diff-profile:<name>` | Show what would change switching to a given profile |

Note: commands that don't require zenki to be running (e.g. `list-profiles`,
`show-profile`) should work even when invoked on a freshly starting v7 before
other zenki are up.

## Setup Wizard (start-set-up.setup)

`start-set-up.setup` is an ordinary profile — invoked explicitly via
`Protocol-7 v7[setup]` or automatically on first run when no host profile
exists. It starts only what is needed for the wizard itself (cube, p7-log),
runs the configuration interface, and writes `start-set-up.<hostname>`. The
user then restarts normally and auto-detection picks up the generated file.

The wizard is a standalone script or minimal TUI zenka — NOT an intercepting
zenka that wraps v7's startup flow. Interface options:

- **TUI**: terminal checklist (preferred for initial setup, no dependencies)
- **Web**: served by httpd once running (preferred for reconfiguration)

Hardware detection informs profile suggestions:

```perl
## detected at wizard start and stored in generated profile as comments
## GPU: RTX 3060, 12GB VRAM → development / vision profiles viable
## RAM: 64GB               → full profile viable
## CPU: 16 cores           → no constraint
```

## Zenka Metadata

For discovery without starting zenki, metadata should live in the start file
or a small descriptor alongside it — NOT in init_code (which requires the
zenka to be loaded). Suggested location:

```
cfg/zenki/<name>/zenka.profile-meta
```

```yaml
name:        Coding Assistant
description: AI-powered code analysis and generation
category:    development
requires:
  ram_gb:    4
  gpu:       optional
suggests:
  zenki:     [ models ]
```

Discovery scans `cfg/zenki/` (not `src/`) since zenka identity
is defined by configuration, not module filenames.

## Implementation Phases

1. **Subname → profile mapping** in `v7/start`: if subname present, load
   `start-set-up.<subname>` directly; if absent, call `v7.resolve_startup_profile`
2. **`v7.resolve_startup_profile`**: hostname → local → setup → base resolution
3. **`start-set-up.setup`**: wizard profile with TUI generator writing host profile
4. **Preset profiles**: minimal, development, vision (as additional start-set-up.* files)
5. **`system.args` command interface**: implement command taxonomy above, starting
   with read-only introspection commands then profile management
6. **Zenka metadata descriptors**: add `zenka.profile-meta` files to key zenki
7. **Web reconfiguration interface**: via httpd once system is running (optional)
8. **Profile inheritance semantics**: define += / -= override syntax

## Command Interface UI Design Principles

### Colour-as-Feedback: The Living Options Table

The `-options` table (see `./bin/amos-chksum -options` for style reference) is
not just documentation — it is the primary feedback mechanism for unrecognised
or ambiguous input. Rather than a separate "not recognised — did you mean X?"
message, the same table is always shown, with colour intensity encoding match
probability across all entries simultaneously:

- **Exact match**: entry at full highlight intensity, rest at resting tone
- **Near match / typo**: closest entries lit proportionally to match score,
  multiple candidates visible at once — ranked by probability through intensity
  rather than by position or prose
- **Genuine ambiguity**: two entries at equal intensity — the system honestly
  represents uncertainty; the user resolves it, not the system
- **No match**: all entries at resting tone — the full table is still the answer

This replaces error states entirely. The interface stays in one mode: showing
options, always — with the colour layer carrying all contextual interpretation.

### Context-Sensitive Form Highlighting

The same table entry shows both `:` and `=` parameter forms. Colour determines
which is primary based on invocation context:

- **nshell / P7 network**: `:` form at primary highlight colour, `=` in softer
  secondary tone on the same line
- **shell / p7c invocation**: `=` form primary, `:` secondary

Same data, same layout — the colour layer silently carries the contextual
recommendation without any conditional prose.

### Dot-Leader Alignment and Optional Syntax

Follow the `amos-chksum -options` visual language:
- Flag / command left-aligned, dot leaders to fixed column, description right
- Optional elements in `[ ]` inline: `set-profile[s]:<name>`
- Both forms on one line where space allows: `[ = set-profile=<name> ]`
- Colour renders in two tones: command token highlighted, description softer

The alignment engine handles variable-length entries automatically — dot leader
width adjusts to the longest entry in the current table so columns always land
cleanly regardless of how many commands are present.

## Notes

- `start-set-up.base` stays unchanged throughout — it is the stable reference
- Multiple named profiles can run simultaneously via subname without conflict
- `system.args` command design was intentionally deferred until now because
  the option space was too broad to commit to partially; designing alongside
  the profile system gives a coherent frame
- `-no-config` / `auto_start: true` flag for automation / headless deployments
  should be addressed in phase 5 alongside the args interface
