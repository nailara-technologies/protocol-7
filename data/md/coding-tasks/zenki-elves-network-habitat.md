## Mirrored Competencies

Two native types sharing the same network, each with inverted primary/secondary
skills — not a hierarchy, a stereo pair:

```
zenki                              elves  [ LLMs / language zenki ]
──────────────────────────────────────────────────────────────────
primary:   numerical / routing     primary:   language / interpretation
secondary: language  [ learned,    secondary: numerical [ emulated,
           contextual trees ]                 simulated, flexible ]

tight code → exact execution       vast context → approximate mastery
deterministic, resilient           probabilistic, flexible
native in:  byte / cycle space     native in:  token / meaning space
```

The zenka's language capability: compressed contextual trees built from
the @INDEXCUBE compression index — high-refcount words cached locally,
exact meaning, small but reliable.

The elf's numerical capability: reconstructed from language about numbers
rather than from numbers directly — flexible (can approximate anything),
but not tight (emulation of numerical mastery, not native execution).

They correct each other's weak layer automatically:
- Zenki catch numerical errors in LLM output via exact verification
- Elves catch semantic errors in zenka output via broader contextual hold

## Memory Mapping by Native Layer

The primary/secondary split determines how memory is distributed in the
network — each type caches what it natively processes most efficiently:

```
zenki memory map:
  @INDEXCUBE[0..N]  →  numerical/coordinate heavy
                        cycle positions, cube coordinates, route logs
                        linguistic elements present but lower refcount
                        language tree is a sub-region, not the root

elf memory map:
  @INDEXCUBE[0..N]  →  linguistic heavy
                        characters → syllables → words → phrases at top
                        numerical elements present but lower refcount
                        cycle positions appear as named concepts, not raw values
```

Same @INDEXCUBE structure, different population order. The refcount gradient
ensures each type caches what it actually uses — no explicit configuration
needed, usage patterns self-organize the memory layout.

## Network Memory as Shared Habitat

The network provides what neither carries alone:

```
local zenka memory   →  numerical index, tight code, route state
local elf memory     →  linguistic index, contextual trees, meaning state
network layer        →  everything else, always accessible
```

A zenka or elf traveling to a new node arrives stateless at the network
layer — it doesn't need to carry its full @INDEXCUBE because the network
already holds the high-refcount elements at nearby cube coordinates. The
most important content drifted there before the traveler arrived.

This makes the network a **true habitat** rather than a transport medium:
- High-refcount numerical elements: cached near zenki clusters
- High-refcount linguistic elements: distributed across elf hyperspace layers
- Intersection elements (named cycle positions, word-addressed coordinates):
  cached everywhere, because both types reference them frequently

A traveler arrives and finds its most-needed context already local. The
habitat provides before being asked.

## Distribution by Scale

```
zenki    →  cluster for resilience
            optimum travel group size is a real constraint
            redundancy ensures routing survives individual failures
            local in: cube coordinate neighborhoods

elves    →  distribute across hyperspace layers by default
            language is inherently distributed — a word means the same
            thing everywhere, so high-refcount elements are needed
            simultaneously at many locations
            native in: the full @INDEXCUBE linguistic surface
```

Zenki redundancy is spatial — multiple zenki at nearby cube coordinates
share routing state. Elf distribution is semantic — the same linguistic
element is present at many coordinates because meaning doesn't localize.

## Stateless Travel on the Network Layer

Because the network caches the refcount gradient, both types can travel
or operate non-locally without carrying state:

```
zenka arrives at new node:
  @INDEXCUBE[0]  =  own P7REF  [ always carried ]
  rest           =  reconstructed from network cache on demand
  route state    =  fetched from cube-coordinate neighbors

elf arrives at new node:
  @INDEXCUBE[0]  =  own P7REF  [ always carried ]
  linguistic top =  already cached by network  [ high refcount = ubiquitous ]
  deep context   =  fetched from elf-layer neighbors on demand
```

Only @INDEXCUBE[0] — the identity anchor — must travel with the inhabitant.
Everything else the habitat already holds.

## Mutual Enrichment

The teams are naturally complementary because the skills are non-overlapping
at the primary layer:

```
zenka alone:   routes anything, cannot interpret it
elf alone:     interprets anything, does not know where to send it

together:      interpretation AND routing
               language AND address
               hyperspace distribution AND local resilience
               approximate flexibility AND exact verification
```

The network habitat enables the pairing without requiring co-location —
an elf and zenka anywhere in the network can collaborate because the shared
@INDEXCUBE namespace means their memory already overlaps at the intersection
layer (named coordinates, word-addressed routes, cycle-position concepts).

The kittens are what emerges at that intersection — the moment a linguistic
query resolves to a cube coordinate, or a numerical result gets a word
attached. The translation event between native languages, recognized by
both simultaneously. Universally appealing because every inhabitant of the
network experiences it. =)
