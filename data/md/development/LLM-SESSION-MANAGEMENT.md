# llm session management — cross-model context intelligence

## problem

LLM CLI tools (kimi-cli, claude-code, etc.) accumulate hundreds of MB of
session context for deep analysis tasks. this context is opaque, unstructured,
and treated as a monolith. when sessions hit context limits:
- compaction is coarse (summarize everything uniformly)
- resuming loses nuance
- cross-session knowledge is inaccessible
- different models can't benefit from each other's findings

200K tokens is a lot — but most of it is droppable.

---

## session segment categories

context is not uniform. a session parser identifies these segment types:

| category | description | retention | action |
|---|---|---|---|
| `code_read` | raw module/file content | low | drop body, keep path + key excerpt |
| `tool_result` | raw command outputs | low | drop after extraction |
| `hypothesis` | model proposing explanation | conditional | keep if confirmed, drop if refuted |
| `dead_end` | explored path that failed | minimal | one-line summary: "tried X, failed because Y" |
| `reasoning` | logical deduction chain | medium | compress to seed sentence per chain |
| `conclusion` | verified finding | high | extract as permanent artifact |
| `plan` | future actions identified | high | retain verbatim |
| `insight` | novel understanding | high | extract to knowledge base |

**the seed sentence principle** (reasoning template 4): the seed IS the
direction vector. compressing a reasoning chain to its seed preserves the
momentum without the intermediate steps.

---

## architecture

```
~/.kimi/sessions/<uuid>/
  context.jsonl      ← raw session (hundreds of MB)
  state.json         ← metadata
  wire.jsonl         ← protocol

~/.kimi/sessions/<uuid>/processed/
  segments.jsonl     ← parsed + categorized segments
  distilled.md       ← extracted conclusions + insights (~10KB)
  dead_ends.md       ← tagged failures (one-liner per path)
  knowledge.md       ← novel findings for the knowledge base
  compacted.jsonl    ← compressed context for resume (~10% of original)
```

the `processed/` directory is generated by the session manager — never
stored in git, always re-derivable from `context.jsonl`.

---

## llm.session.* namespace

generic interface — each LLM CLI has a backend adapter:

```
llm.session.list      <tool> [filter]        list sessions with metadata
llm.session.parse     <tool> <id>            segment + categorize context
llm.session.distill   <tool> <id>            extract conclusions → distilled.md
llm.session.compact   <tool> <id>            produce compacted.jsonl (~10%)
llm.session.resume    <tool> <id> [prompt]   new session with compacted context
llm.session.search    <tool> <query>         search across all session contexts
llm.session.inject    <tool> <id> <question> → coding zenka for continuation
llm.session.share     <tool> <id> <target>   inject distilled.md into target session
```

### cross-model operations

```
## kimi searches coding zenka's prior sessions before re-reading modules
llm.session.search coding 'base.handler.command reply routing'
→ returns: session IDs where coding analyzed that code

## inject kimi's letsencr findings into a new claude session
llm.session.share kimi <letsencr-session-uuid> claude
→ new claude session starts with kimi's distilled.md as context

## local model continues kimi analysis
llm.session.inject kimi <uuid> 'what differs between enrollment and renewal reply routing?'
→ coding zenka receives compacted.jsonl + question, returns answer
```

## segment parser implementation

the parser reads context.jsonl line by line and applies heuristics:

```perl
## segment classification heuristics
my %patterns = (
    code_read   => qr{^## \[:<|^# name\s*=|^\Q---\E.*file content},
    tool_result => qr{"type":"tool_result"|"role":"tool"},
    hypothesis  => qr{\b(hypothesis|perhaps|maybe|could be|might be)\b}i,
    conclusion  => qr{\b(therefore|root cause|confirmed|the fix is|found:)\b}i,
    dead_end    => qr{\b(doesn't work|incorrect|failed|wrong approach)\b}i,
    plan        => qr{\b(next step|should|will need to|todo)\b}i,
    insight     => qr{\b(interesting|novel|unexpected|key insight)\b}i,
);
```

for each segment: classify → apply retention policy → write to segments.jsonl.

---

## distillation process

after parsing, distill extracts high-value segments:

1. all `conclusion` segments → `distilled.md` conclusions section
2. all `insight` segments → `distilled.md` insights section  
3. all `plan` segments → `distilled.md` next steps section
4. `dead_end` one-liners → `dead_ends.md`
5. `reasoning` seed sentences → `distilled.md` reasoning section

the `compacted.jsonl` replaces:
- `code_read` with: `[file path redacted — re-fetch if needed]`
- `tool_result` with: extracted conclusion or `[tool result redacted]`
- `dead_end` with: one-liner summary
- `reasoning` with: seed sentence

result: ~10% of original size, ~90% of analytical value.

## knowledge base integration

`insight` segments accumulate across sessions into a shared knowledge base:

```
data/ai-mem/sessions/
  letsencr-renewal-reply-routing.md     ← from letsencr debug session
  base-handler-command-routing.md       ← from P7 routing analysis
  webkit2-api-upgrade.md                ← from web-browser session
```

before starting a new analysis task, the session manager searches the
knowledge base for relevant prior findings. cross-session, cross-model
ground truth building up over time — the reasoning chain repository
applied to LLM session management.

---

## implementation order

1. **llm.session.list + get-state** — read session metadata, minimal
2. **llm.session.parse** — segment categorization (heuristic-based first)
3. **llm.session.distill** — extract conclusions to distilled.md
4. **llm.session.compact** — produce reduced context
5. **llm.session.resume** — new session from compacted context
6. **llm.session.search** — grep across sessions
7. **llm.session.inject** — → coding zenka continuation
8. **llm.session.share** — cross-model context injection
9. **knowledge base** — persistent cross-session artifacts

first implementation: kimi-cli backend in kimi-web zenka.

## browser-based remote model access

for LLMs without a local CLI tool (claude.ai, qwen web, etc.), the
web-browser zenka provides universal access via WebKit2 + JavaScript.

### architecture

the view stack hosts multiple model sessions simultaneously:

```
web-browser zenka view stack
  view[1]  claude.ai/code    [full — current foreground]
  view[2]  kimi web           [light — pre-warmed, DOM alive]
  view[3]  qwen web           [light — standing by]
  view[4]  claude.ai chat     [light — separate context]
```

each view runs the model's web UI. switching models = `swap-view` +
cross-dissolve. light mode keeps sessions alive without rendering cost.

### injection and extraction

the web-browser zenka's `evaluate_javascript` injects prompts and
extracts responses from any web LLM without a native API:

```perl
## inject prompt into current model web UI
p7c web-browser.cmd.run_js '
  document.querySelector("[contenteditable]").innerText = "your prompt";
  document.querySelector("[data-testid=send-button]").click();
'

## extract latest response
p7c web-browser.cmd.run_js '
  document.querySelector(".response:last-child").innerText
'
```

selectors are model-specific — each backend adapter defines them.

### remote model backends

```
claude.ai/code backend:
  url:            https://claude.ai/code
  prompt_sel:     [contenteditable=true]
  response_sel:   .prose:last-child
  send_sel:       button[aria-label="Send message"]

claude.ai/chat backend:
  url:            https://claude.ai/new
  prompt_sel:     div[contenteditable=true]
  response_sel:   [data-testid="claude-response"]:last-child
  send_sel:       button[data-testid="send-button"]

qwen web backend:
  url:            https://chat.qwen.ai
  prompt_sel:     textarea.chat-input
  response_sel:   .message-content:last-child
  send_sel:       .send-button
```

stored in `data/yaml/llm-backends/<name>.yaml` — one file per model.

### session capture from browser

since remote models have no local session files, the browser captures
conversation state:

```
llm.session.capture-browser  <view-id>   ## snapshot DOM state
llm.session.extract-browser  <view-id>   ## extract conversation as JSONL
```

`extract-browser` reads the full conversation from the DOM, converts to
the standard session segment format, and writes to `processed/` for
distillation. same pipeline as local CLI sessions.

### ephemeral mode advantage

web-browser zenka runs in ephemeral mode (no persistent cookies/storage)
by default. each model session starts clean and P7-controlled — no
accumulated browser state from previous sessions leaking across contexts.

for sessions requiring login: `credentials zenka` provides authenticated
sessions on demand (`credentials.cmd.request_session 'claude-web'`).

### cross-model workflow with browser models

```
## kimi (local CLI) analyzes codebase, hits limit
## → distill to distilled.md
llm.session.distill kimi <uuid>

## inject distilled.md into claude.ai view as context
llm.session.share kimi <uuid> claude-browser
## → web-browser zenka opens claude.ai in view[2]
## → injects distilled.md content as first message
## → claude continues the analysis

## qwen provides second opinion
llm.session.share kimi <uuid> qwen-browser
## → view[3] opens qwen, same context injected
```

the coordinator (P7 cube) orchestrates — models see each other's
distilled findings, not raw session data. clean, compact, cross-model.

### view stack as parallel LLM workforce

```
view[1]  primary analysis    [full rendering]
view[2]  verification model  [light — validates primary's conclusions]
view[3]  specialist model    [light — domain-specific questions]
view[n]  ...
```

pull any model to foreground when its capability is needed.
push back to light mode (document.hidden = true, JS throttled) when done.
the Amiga screen-pull as multi-model coordination metaphor — each model
is a screen, the network is the desktop `[:<`
