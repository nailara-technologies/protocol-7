found 2026-08-21 extracting content misplaced into
`cfg/zenki/{git,work,workspace-transfer}/source` (see
[[deps-os-short-leaf-names]] and the `deps/` ambiguity-cleanup rename):
25 stray files, several with real p7-module headers (`## [:< ##`,
`# name = ...`, `# descr = ...`) that looked plausible at a glance.
`grep -l PLACEHOLDER_FOR_AMOS7_SIGNATURE` instantly separated 18 of
them (draft exec-wrapper stubs, all traced to either dead references
or exact duplicates of real working code) from genuine content (3
planning docs with no fake marker, real prose, needed relocating not
deleting).

**why this works**: this repo's real signing pipeline
(`bin/Protocol-7 sourcecode update-signatures`) writes an actual
AMOS7 checksum block, never the literal string `PLACEHOLDER_FOR_
AMOS7_SIGNATURE_LINE_1/2/3`. Seeing that exact placeholder text is
unambiguous proof a file was generated by a model imitating the
convention's *shape* without ever running it through the real signer
— i.e., it was drafted and left, not integrated.

**how to apply**: before deciding whether a suspicious/misplaced file
in this repo is real, finished work or abandoned scratch:
1. `grep -l PLACEHOLDER_FOR_AMOS7_SIGNATURE <file>` — instant, free
   signal if present.
2. cross-check with [[rename-scope-policy]]'s sibling lesson: does an
   equivalent already exist elsewhere (e.g. `src/<zenka>.cmd.<name>`)?
   If content matches near-exactly, the stray file is superseded, not
   just unsigned.
3. `grep -rl '<the file's own name>'` across `src`/`cfg`/`data` — if
   nothing references it, it was never wired in.
Only after all three come back "orphaned" is it safe to delete outright
rather than migrate/archive. If it describes real unbuilt
functionality (not just a duplicate), write a task file capturing the
design before deleting — see
[[workspace-transfer-external-bridge-commands]] for the pattern
(table of what each stub delegated to + why it matters, not a verbatim
code dump).

**Inverse failure mode, found 2026-08-22**: the placeholder convention
itself can be malformed by a dispatched agent that's imitating the
*shape* without the exact form. A kimi k2.7 dispatch (9P Tcreate/
Tremove work) produced all 8 new files with the marker text merged
INTO the structural signature-block skeleton lines (e.g.
`#\\\|PLACEHOLDER_FOR_AMOS7_SIGNATURE_LINE_2 \ / AMOS7 \ YOURUM ::`)
instead of the clean, separate 4-line form
(`# PLACEHOLDER_FOR_AMOS7_SIGNATURE_LINE_1` through `_4`, nothing
else) every other file uses pre-signing. Confirmed by diffing against
this session's own already-signed files: the real signer fully
replaces a clean placeholder block with fresh content regardless of
what came before, so there was no need for kimi to draft a skeleton at
all — and a malformed one risks the signer failing to recognize/
replace it, or producing the double-footer bug (see
`bug-signature-endline-restoration.md`). Caught only by reading each
new file's tail during review, not by any automated check.
**How to apply**: when reviewing a dispatched agent's new files before
signing, check the placeholder footer is the plain 4-line form and
nothing more — don't assume a plausible-looking signature-shaped block
is correct just because the marker text is present somewhere in it.
