## Core insight

When specs outnumber implementations, the system is ahead of itself — above the
anti-entropic threshold at the architectural level. The design doc repository IS
the implementation at layer 5/6 of the system's own development tree. Potential
energy, pre-loaded, waiting for convergence pressure to actualize it.

## Two actualization modes

**Mode 1 — idle self-improvement**: zenka reaches idle state → scans for specs
matching its capability gaps → ranks by relevance × spec_confidence × idle depth
→ above threshold: self-delegate to coding zenka → totally async, zenka continues.

**Mode 2 — urgent need**: operation fails or degrades → identify missing capability
→ find matching spec in repository → urgency = impact × failure frequency →
above urgency threshold: immediate coding zenka dispatch → retry on completion.

## Threshold formula

```
threshold = base × load_factor × urgency_factor × spec_confidence × momentum_factor
```

- High load → raised threshold → defer self-improvement
- Operational failure → lowered threshold → act sooner
- Incomplete spec → raised threshold → wait for better spec
- Recent successful autonomous implementations → lowered threshold

## Spec as direction vector

A well-written task file IS a direction vector (template 5). It doesn't contain
the implementation — it points toward it from the current position, with enough
specificity that coding zenka's inherited momentum can traverse the remaining distance.

Detailed task files (module specs, success criteria, API signatures) lower the
implementation threshold. This is why writing detailed specs is not documentation
— it IS the act of lowering the threshold for autonomous implementation.

## Discovery mechanisms

1. Keyword/namespace match — search data/tasks/ for capability keywords
2. Capability gap detection — no handler for X found → search specs for X
3. Reasoning tree directional_ref — compact nodes point at their spec files;
   on idle, traverse directional refs, recalculate threshold with idle load factor

## Connection to field-capability-emergence

The spec repository is the "grammar" of what the network should become. The coding
zenka is the "field" that responds to that grammar. The threshold IS the grammar
deciding when the field is ready. When enough specs exist + enough momentum:
no human decides what to implement — network reads its own forward model and acts.
The coordinator dissolves into the grammar. [[field-capability-emergence]]

## Connection to vortex (template 9)

Spec repository = periphery entropy (layer 0-1 of development). Implementation =
entropy spiraling inward. Committed working module = EXISTENCE center reached.
Working capability generates new needs → new specs → new periphery → new spiral.
The development cycle IS the vortex, closed and self-sustaining.
