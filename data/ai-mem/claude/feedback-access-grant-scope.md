When a command is denied to the `taeki`/admin user, do NOT add a
per-zenka `access.zenki` grant for that user — `taeki` already has full
wildcard access at the cube level.

**Why:** user corrected a kimi-added
`access.cmd.usr.unix-taeki = eval-code exec-sub` entry in
`configuration/zenki/transport/access.zenki` as redundant
(2026-06-15, transport.eval-code/F16 fix).

**How to apply:** for "no perm" fixes, only two things are normally
required:
1. `<zenka>/start` — add the module group (e.g. `devmod`) to
   `modules.load` so the command compiles/loads at all.
2. `<zenka>/start`'s `access.cmd.usr.cube` list — add the bare final
   command name. THIS is the real access-control gate.

**Correction (2026-06-20):** `access.cmd.usr.cube` entries can ONLY
ever be bare command names — no dots, no namespacing at all. Writing
`self_test.run` / `self_test.status` there (an attempt to disambiguate
which module they referred to) silently matches nothing; the list does
plain bare-string comparison with zero dot-awareness. Stripping the
prefix is the only way an entry resolves at all — but that then exposes
the real downstream risk: bare-name collisions. The list is a flat
namespace of final command names (the part after `.cmd.`), so two
unrelated `.cmd.` modules both ending in `status` will collide and
silently overwrite each other's routing. Fix collisions by renaming the
colliding `.cmd.` module(s) to a more specific bare suffix (e.g.
`coding.self_test.cmd.self-test-status`), not by trying to qualify the
access-list entry with a prefix — qualification doesn't work here.

Separately: `subroutines.load-early` (auto-generated by
`gen-sub-whitelist <zenka>`) is NOT an access gate — it only controls
eager preload vs. lazy-load timing of subs and should never block a
call. If regenerating it ever appears to fix a "no perm" error, look
for the actual cause elsewhere (e.g. it coincided with an access-list
fix, or a module file went missing from disk after the zenka started).

`configuration/zenki/cube/access.zenki` is only needed for *cross-zenka*
access (one zenka calling another's command), per
[[feedback-buffer-access-control]]. Per-zenka `access.zenki` user grants
are for non-admin users; don't add them for `taeki`.
