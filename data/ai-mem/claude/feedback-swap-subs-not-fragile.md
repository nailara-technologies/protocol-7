`base.swap_subs`-based namespace aliasing (e.g. `base.strm.subscribe` ->
`strm.subscribe`, `base.zenka.push` -> `zenka.push`, `base.dependency` ->
`dependency`) is NOT fragile and is not a reason to avoid adopting the
pattern for another module. Do not flag "the whitelist step might be
missed" as a correctness risk.

**Why:** I (assistant) initially argued against moving `base.strm.local.*`
into the `strm.local.*` namespace, citing gen-sub-whitelist as a fragile
manual step that could silently break call sites. User corrected: the
sub-whitelist only gates *lazy loading*, not availability, and is
generated by script (`bin/dev/gen-sub-whitelist <zenka>`) — running that
script is a mechanical, low-risk part of the swap, not a hazard. The only
genuine weak point is documentation/discoverability: swapped namespaces
aren't enumerated anywhere central (scattered mentions only in
`data/yaml/project-context/workflow-zenka-patterns.yaml` and
`data/md/design/CODE-NAMESPACE-AND-SIGNING-INFRASTRUCTURE.md`, nothing in
CLAUDE.md), so a model reading `<[base.strm.local.X]>` call sites cold has
no signal this convention exists or is sanctioned. That's a docs/tooling
gap, not a reason to distrust the swap mechanism itself.

**How to apply:** When evaluating whether to `swap_subs`-alias a `base.*`
module into a shorter namespace, judge it on: (1) whether the module is a
generic/reusable pattern worth a short call name, (2) the number of
existing call sites to migrate, (3) whether it's worth the churn — but
never cite the whitelist step itself as a risk. Separately, flag the
missing canonical "active namespace swaps" reference as a real
documentation debt worth fixing (see [[project-swap-subs-doc-gap]] if
that memory exists, otherwise this is the seed of it).

**Concrete miss, 2026-07-23** (log-anonymization phase 1 landing,
`dbd7ca8ba`): wrote new `p7-log.anon.store`/`.resolve` code calling
`<[base.file.zenka_dir.data_path]>`, the pre-swap name — `base.file.
pre_init` swaps the whole `base.file.*` group to `file.*`, so the live
callable is `<[file.zenka_dir.data_path]>`. Also nearly "fixed" a
correct call (`<[chk-sum.bmw.L13-str]>`, already post-swap) by reverting
it back to the pre-swap `base.chk-sum.bmw.L13-str` — user caught it
before it landed. Rule of thumb before calling any `base.X.Y` primitive
from new code: `ncode s src:base.X swap_subs` first to check whether
that group gets renamed at init, and call the post-swap name if so.
Separately, this session's whitelist gap (new `base.file.zenka_dir.
data_path` reference wasn't in `p7-log`'s `subroutines.load-early`) was
fixed by hand-editing the file rather than running `bin/dev/gen-sub-
whitelist <zenka>` (confirmed still present on disk) — worked fine for
this one-line addition, but the script is the canonical tool and should
be preferred for anything bigger.
