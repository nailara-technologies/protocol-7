**Modules added** (all under `src/jobsite.report.*` + two `.cmd.` wrappers):
- `jobsite.report.csv_parse` — parses periodic bewerbungen-csv exports (simple 4-col + extended 10-col formats), with quote-balance tracking to rejoin physical lines when a quoted field contains an embedded real newline (previously truncated rows, dropping the URL column and breaking dedup).
- `jobsite.report.assemble` — merges csv snapshots + live jobsite records, dedup by stepstone-id-in-url else normalized title+company, keeps latest snapshot, live records always win. `status_map` maps `'rückmeldung'`/`'responded'` → `'applied'` (NOT `'interviewed'` — a generic reply is not proof of an interview; only literal `'vorstellungsgespräch abgeschlossen'` counts).
- `jobsite.report.render_html` — lightweight kept-as-is summary table renderer (first version; not removed per user's explicit "do not revert" instruction).
- `jobsite.report.evidence_collect` — gathers CV (most-recent file in `cv_dir`), reference docs (Arbeitszeugnis etc.), and application letters (matched to entries by company-name substring).
- `jobsite.report.extract_text` — `.html` via `HTML::TreeBuilder`+`HTML::FormatText`, `.pdf` via `pdftotext -layout` (safe list-form open, no shell interpolation).
- `jobsite.report.mail_split` — mbox → individual RFC2822 messages, mboxrd `>From` unescaping.
- `jobsite.report.mime_decode_body` — recursive multipart MIME decoder. Key bug fixed: boundary token was extracted from the *lowercased* Content-Type string, silently breaking case-sensitive boundary matching on mixed-case boundaries and merging all parts into visible garbage — fixed by extracting boundary from the original-case header value. Also does link/tracking-URI stripping and invisible-Unicode/blank-line cleanup.
- `jobsite.report.mail_evidence_collect` — most-iterated module. Filters by recipient alias (`jobs@`), excludes jobcenter/Bundesagentur addresses and marketing noise, excludes the user's own outgoing addresses via [[feedback-no-personal-data-in-repo-tree]]'s `file.zenka_dir.load` pattern (so a courtesy reply to a rejection isn't miscounted as company feedback), exact-duplicate guard, "last known state per matched job" dedup.
- `jobsite.report.render_dossier` — full 6-section evidence dossier template (Übersicht / CV / Arbeitszeugnisse / Bewerbungsschreiben / Rückmeldungen / Eingangsbestätigungen), visually redesigned to match the purple/indigo palette pulled from the user's own application-letter HTML, fixed print-pagination (removed `page-break-inside: avoid` that was forcing large blocks fully onto the next page and leaving big blank gaps).
- `jobsite.cmd.report-build` / `jobsite.cmd.dossier-build` — cube-facing wrappers, `.cmd.` reply contract requires string data (not hashref) — use `sprintf`.

**Config** (`cfg/zenki/jobsite/zenka.v7`): added `csv_import_dir`, `report_dir`, `cv_dir`, `applications_html_dir`, `reference_docs_dir`, `mail_dir`, all pointing under `/data/jobcenter-report-data/` (external, not in repo — personal data). `report-build`/`dossier-build` added to `access.cmd.usr.cube`.

**How to re-render for a different period** (e.g. a caseworker asking for a shorter window): both commands take plain positional `<from> <to>` (YYYY-MM-DD each), no other setup needed —
```
p7c jobsite.dossier-build 2025-04-10 2026-08-02   ## full evidence dossier
p7c jobsite.report-build  2025-04-10 2026-08-02   ## lightweight summary-table only
```
**Param format history**: originally implemented as a JSON arg (`'{"from":"...","to":"..."}'`), matching a pattern seen in ~46 other `.cmd.` modules across the codebase — but that pattern is for web/UI-facing endpoints (browser↔backend), not a general backend convention. `jobsite`'s own sibling `.cmd.` modules (e.g. `jobsite.cmd.set-status`, `args = "<id> <status>"`) use plain space-separated positional args instead — the actual native P7 backend convention. User corrected this and asked for the conversion; converted both commands to `split ' ', $args` positional parsing. Also noted in passing: the project is trending away from JSON as an intermediate format generally (moving some file-based use cases to YAML, with planned seamless format conversion between them) — JSON wasn't wrong/bloated here, just not the native choice for a non-UI-facing command.
Output paths are printed in the reply (`report:`/`dossier:`/`html:`), written under `report_dir` (default `/data/jobcenter-report-data/reports/`) as `<from>_<to>.yaml` + `<from>_<to>.dossier.html` (or `.html` for the summary version). Delete the existing `<from>_<to>.*` files first if re-running the *same* period after a code change — `jobsite.report.assemble` overwrites its own output file but the caller (`v7.restart jobsite` after any module edit) is still required for code changes to take effect, per the reload-regression note above.

**Known upstream bug hit hard during this work**: `<zenka>.reload` does not reliably recompile already-loaded `.cmd.` modules on a live process — always use `p7c v7.restart <zenka>` after editing jobsite modules. Documented separately as `data/tasks/loader-reload-stale-cmd-modules.md` (committed, commit `138895123`).

- **Link-stripping regex ate through tag boundaries, leaking attribute text, fixed twice**: `jobsite.report.mime_decode_body`'s link-removal regexes ran `\S+`/`\S*` against raw HTML before parsing (deliberately, per the module's own comment, since stripping after HTML::FormatText runs is unreliable — word-wrap would have already fragmented a long URL). `\S+` treats `<`/`>` as ordinary non-space characters, so it doesn't stop at a tag boundary. Two distinct leak shapes found from this, both by the user reading the actual rendered output: (1) a URL inside a quoted `href="..."` attribute got eaten along with its closing `"`, leaving the tag unparseable and the *next* attribute (e.g. `style="padding:10px 0 0 0;">`) dangling as orphaned text that html::treebuilder's parser-recovery then leaked into the visible output — fixed by neutralizing `href`/`src` attribute values whole (quote-aware, plus an unquoted fallback) to `="#"` *before* the generic bare-url regex runs; (2) a *visible-text* URL sitting directly against the next tag with no whitespace between them (e.g. `...url</a><span style="font-size:9.0pt;...">`) got matched by the same greedy `\S+`, eating straight through the closing/opening tags and orphaning the `<span>`'s attributes the same way — fixed by changing `\S+`/`\S*` to `[^\s<]+`/`[^\s<]*` in both link-stripping regexes so the match always stops before the next tag starts. **Lesson: any regex meant to operate on "one line of raw HTML" before parsing must exclude `<` from its non-whitespace character class, or it will silently eat into neighboring tags whenever the matched content isn't followed by real whitespace — a case easy to miss by eyeballing since the corruption doesn't crash anything, it just leaks the next tag's raw attributes as camouflaged plain text.**
- **Rejection-intent classifier false positive, fixed with a context gate (not word removal)**: the generic word `'leider'` (German "unfortunately") in `%rejection_words` misclassified a live, never-answered recruiter follow-up ("leider konnte ich Sie telefonisch nicht erreichen" — an apology for a missed *phone call*, chasing a still-pending skill-sheet request) as a rejection. (?:positive|bessere|passende|geeignete)`; `zug kommen`; `in betracht`) co-occurs anywhere in the same mail. Also fixed in the same pass: `'nicht berücksichtigt'` (past participle stem) silently never matched the equally common infinitive phrasing `"nicht berücksichtigen können"` — shortened to the stem `'nicht berücksichtig'`; `'nicht ausgewählt'` was flagged by the user as not idiomatic German in this context and removed (never matched any real mail either); `'nicht geklappt'` missed the equally common reordered phrasing `"klappt ... nicht"` — added a dedicated regex `klappt\s+(?:\S+\s+){0,6}nicht` (needed a 6-word gap, not 3, to match a real "klappt es vorher bei denen nicht" case). Net result measured by rebuild: 58 correctly-labeled rejections (vs. the original 59 that included exactly one false positive). **Lesson: German separable verbs and irregular (ablaut) verb stems break naive substring matching on the infinitive form — check the actual past-participle/conjugated forms appearing in real data, and always validate a classifier-keyword change by rebuilding and diffing counts against the real corpus, never by a quick manual grep.**
- **Multipart body-selection bug: an attachment silently replaced the real reply, fixed**: `jobsite.report.mime_decode_body`'s `$walk` sub picks the first `text/plain` leaf found anywhere in the mime tree as the body (`$found->{'plain'} //= $decoded`), with no concept of "attachment vs. body part". One real message (structure: `multipart/mixed` → [`multipart/related` → [`text/html` real reply, `image/png` inline logo], `text/plain; filename=awinia_datenschutz_20180518.txt` privacy-policy attachment]) had its entire extracted content replaced by the attached disclaimer text, because the attachment's `text/plain` leaf was found and claimed the 'plain' slot, and `$result = $found{'plain'} // $found{'html'} // ...` never fell through to the real html reply nested one level deeper. Fixed by skipping any leaf whose Content-Type carries a `name=`/`filename=` parameter or whose Content-Disposition is `attachment`, before it's allowed to compete for a body slot at all. **Lesson: when walking a mime tree for "the body", explicitly exclude attachment-marked leaves — don't just take the first leaf of a given content-type, since a boilerplate attachment (privacy notice, signature image, T&Cs) can silently outrank the actual message content.**
- **A second, unrelated body-selection bug found right after, same symptom (empty evidence-text)**: user recognized this failure mode from personal experience replying to HTML-only mail in mutt ("On <date>, X wrote:" followed by nothing) and asked whether the attachment fix above could cause the same thing for genuine HTML-only mail. It didn't (verified: the attachment filter only matches on `name=`/`filename=`/`Content-Disposition: attachment`, neither of which a normal inline `text/html` alternative part carries) — but investigating surfaced a *different*, real, pre-existing bug with the identical symptom. Root cause: `multipart/alternative` mail commonly ships a `text/plain` sibling that's "empty" in intent but not literally zero bytes after decoding — one stray whitespace/newline byte survives. `mime_decode_body`'s `return if not length $decoded` treated that 1-byte "content" as real, so `$found->{'plain'}` got set to whitespace and permanently won the final `$found{'plain'} // $found{'html'} // $found{'any'}` selection over the real ~970-char html body sitting right next to it. Confirmed by temporarily instrumenting the live module with a debug-log write to `/tmp/mime_debug.txt` (same technique used earlier in the session for the boundary-case and CRLF bugs) — showed `ctype=[text/plain...] bodylen=1 decodedlen=1` right next to `ctype=[text/html...] decodedlen=972` for the same message. Fixed by changing the emptiness check to `return if $decoded !~ /\S/` (require actual non-whitespace content, not just non-zero length). Found and fixed 2 real cases in the live corpus this way (both previously totally empty evidence-items), zero left after the fix. **Lesson: "empty" and "zero-length" are not the same thing for decoded mail parts — a naive `length()` check is fooled by a lone whitespace/newline byte, and because of the `//=`/`//` "first one wins" selection pattern used throughout this module, one falsely-non-empty low-priority part can permanently hide a real, much larger part behind it.**
- **PDF extraction artifacts fixed: Wingdings bullet glyph + repeating page footer spliced mid-list**: `jobsite.report.extract_text`'s PDF branch (`pdftotext -layout`) had two artifacts on the multi-page Arbeitszeugnis reference document. (1) Word/Office-generated PDFs commonly use a symbol-font bullet glyph (found: U+F0B7, Wingdings-range private-use-area codepoint) for list bullets; `pdftotext` preserves the raw codepoint, which renders as a missing-glyph box with no symbol font installed — fixed by replacing the whole PUA range `[\x{E000}-\x{F8FF}]` with a normal `•` (U+2022), general enough to catch whichever specific glyph a given source used without enumerating them. (2) The document's letterhead footer (bank IBAN/BIC line, Geschäftsführer/Registergericht line, Steuer-Nr line) repeats on every page of the original PDF, but `pdftotext` has no page-boundary marker in its text output — the footer ends up spliced straight into the body wherever the page break happened to fall, which in this case landed mid-bullet-list, visually breaking it. Fixed with a company-name-agnostic regex matching on the field labels (IBAN+BIC line, then optional Geschäftsführer/Registergericht line(s), then optional Steuer-Nr line) rather than the specific company text, so it generalizes to other reference/letter PDFs. Also stripped the literal form-feed byte (`\x0C`) pdftotext leaves at each page boundary, which was showing up as a stray control-character artifact once embedded in the html. **Lesson: `pdftotext -layout` is layout-preserving per-page but page-boundary-blind across the whole document — any recurring per-page furniture (footer, header, page number) will get glued into the running text at an arbitrary point and needs its own strip pass, keyed on recognizable field labels rather than exact wording so it generalizes across different source documents.**
- **Follow-up polish on the same PDF, plus a self-inflicted ordering bug**: (1) a short, heavily right-indented title line ("Zeugnis") landed glued directly to the next paragraph with zero blank line, even though the source pdf has real vertical whitespace there — fixed with a heuristic regex inserting a blank line after any short (`.{0,20}`), heavily-indented (10+ leading spaces) line immediately followed by a non-blank line. (2) bullet indent was inconsistent between the page-1 and page-2 halves of the same list (`pdftotext -layout` re-derives each bullet's column position from absolute pdf coordinates independently per page, so a font-metric rounding difference between pages shows up as a different leading-space count) — fixed by normalizing every `•`-prefixed line to a fixed `  • ` indent, `s/^[ \t]*•[ \t]*/  • /mg`. That normalization initially still failed on exactly the page-2 bullets, which turned out to be self-inflicted: the form-feed (`\x0C`) strip added in the previous fix ran too *late* in the pipeline, so at the time the bullet-indent regex ran, the page-2 bullet line still had a leftover `\x0C` byte sitting between the `^` line-start anchor and the actual leading spaces — `^` in Perl multiline mode anchors right after the preceding `\n`, lands exactly on that form-feed byte, and since `\x0C` isn't in the `[ \t]` character class the anchored match failed silently for that one line only. Fixed by moving the form-feed strip to run first, before every other `^`-anchored cleanup regex. **Lesson: order matters for chained `^`/`$`-anchored text cleanup regexes — a leftover non-whitespace control byte from an earlier bug fix can silently break a later regex's line-start anchor for exactly the lines that byte touches, while leaving every other line looking fine; when a regex fix "mostly" works except on lines right at a known artifact boundary, suspect stray bytes from a previous cleanup step still sitting there.**
- **Final round: gave up on aligning continuation-line indent, merged instead**: normalizing the bullet *marker*'s indent (previous fix) only fixed half the problem — each item's wrapped continuation lines still kept whatever per-page indent `pdftotext -layout` derived, so continuation lines under a page-1 bullet sat at a different column than continuation lines under a page-2 bullet, even with identical bullet-marker alignment. Rather than try to re-derive a "correct" indent per page (fragile, page-layout-dependent), `jobsite.report.extract_text` now merges each bullet item's wrapped lines into one single logical line in Perl (walk lines, track an `$in_bullet` flag, append trimmed continuation lines to the previous line in `@out`) and relies on the existing `white-space: pre-wrap` CSS to let the browser reflow it naturally — sidesteps the indent-matching problem entirely instead of solving it. Caught one side effect from the merge itself before shipping: German compound words hyphenated across the original PDF's line wrap (e.g. "Wetter-" / "Anzeigesystem") were rejoining with a stray space ("Wetter- Anzeigesystem") since the merge always inserted `' '` between lines — fixed by checking whether the accumulated line already ends `\S-` (a real trailing hyphen) and, if so, concatenating flush against it instead. **Lesson: when line-wrap-derived indentation can't be reliably reconstructed per-source, don't keep chasing exact alignment — collapse the wrapped text back to one logical line and let the render target's own line-wrapping do the job; but check the seams where lines get glued back together, since a naive always-insert-a-space join can introduce its own new artifact at exactly the points the original line-wrap happened to fall (hyphenated word breaks).**
- **Same ordering mistake a third time, different regex**: after the merge, a visible blank line still split the list in two right at the former page break — the blank-line-between-two-bullets collapse pass (added alongside the merge) was correct in isolation but ran *before* the footer-strip regex, so at collapse-time that gap was still footer text, not yet blank, and the collapse had nothing to act on. Fixed by moving the footer-strip regex to the very top of the pipeline (right after the form-feed strip), ahead of every regex that depends on its output already being gone. Final pipeline order in `jobsite.report.extract_text`'s pdf branch: strip form-feed → strip repeating footer → swap PUA bullet glyphs → normalize bullet indent → merge continuation lines + collapse the footer's blank-line gap → fix glued title spacing. **Lesson (recurring across all three fixes in this section): every cleanup regex in a chained pipeline implicitly depends on which artifacts the regexes before it have already removed — when a fix "should" work but silently doesn't for a specific interior case, check pipeline order before doubting the regex itself.**
- **The line-merge approach above was wrong and got reverted**: user reported it back as "definitely broken" — merging each bullet item into one logical line and relying on `white-space: pre-wrap` browser reflow has two real problems that only show up once actually rendered: plain preformatted text has no concept of a hanging indent, so once the browser soft-wraps a long merged line, the wrapped portion starts flush at column 0 instead of aligning under the bullet text; and with no blank line or margin between merged one-line items, consecutive bullets read as one dense run-on block instead of a list. **Final, correct approach**: keep every physical line separate (real `\n` between wrapped lines AND between items) and instead re-indent each continuation line's leading whitespace to a fixed `'    '` (4 spaces, matching the `  • ` marker's 4-char width) so both sides of a former page break line up under the same column. The blank-line-between-items collapse logic (for the footer's old gap) was updated to match: a line counts as "part of the list" if it's a bullet marker OR a re-indented (`^    \S`) continuation line, not just a literal bullet-prefixed line. **Lesson: "let the render target reflow it" only works when the render target actually has the structural information needed to reflow it correctly (real `<li>` markup, or CSS hanging-indent) — plain preformatted text with `pre-wrap` does NOT carry per-item indent metadata across a soft line-wrap, so collapsing structure into fewer lines and trusting the browser to "figure it out" loses information silently; a plausible-sounding simplification needs to be checked against the actual rendered/visual result, not just against the raw text output, before treating it as a fix.**

- **Title-line fix corrected again: left-aligning lost real layout intent, replaced with an actual centered `<span>`**: user checked the source pdf directly and confirmed "Zeugnis" genuinely IS centered there — left-aligning it (previous fix) was a plausible-looking but wrong simplification, same mistake-shape as the earlier line-merge revert. Since `jobsite.report.extract_text` only returns plain text (shared by cv/reference/letter extraction, no markup capability), it can't emit real HTML directly — solved by wrapping the detected title in `\x01CENTER\x01...\x01ENDCENTER\x01` sentinel markers, consumed downstream by `jobsite.report.render_dossier`'s shared `$esc` HTML-escape closure, which converts the marker to `<span style="display:block;text-align:center">...</span>` once escaping is done. **Non-obvious gotcha hit immediately**: the marker match failed on the first attempt because `HTML::Entities::encode_entities` (which `$esc` always calls first) had already turned every literal `\x01` byte into its numeric entity form `&#1;` by the time the marker-replacement regex ran — the regex needed to match the POST-escape representation (`&\#1;CENTER&\#1;...`), not the raw control byte. **Lesson: a plain-text extraction module can still express real layout structure (centering, emphasis) to its HTML-rendering counterpart via an out-of-band sentinel marker unlikely to collide with real content — but remember any escaping step downstream will transform that marker too, so match against what the marker *becomes* after escaping, not its original raw form.**
- **Self-inflicted CSS syntax bug: Perl `##` comment style used inside a CSS `<style>` block**: the symmetric-padding fix above landed with a multi-line comment written in this project's habitual Perl module comment style (`## text ##`) instead of valid CSS `/* text */` — since `.evidence-item`'s `dossier.html` template is HTML/CSS, not Perl, the browser couldn't parse the `##` lines as a comment, and dropped the entire malformed declaration block silently (including the real `padding: 0.8rem 2.2rem;` rule right after it) rather than erroring visibly. Result: 0px padding, exactly as if the fix had never been applied, with no error to signal why.
