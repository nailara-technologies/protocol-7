owner 2026-11-07, after deleting an 800+ item invoke render queue by hand [ invoke offers no way to edit it ] :

- the linear queue is the problem, not just the missing editor. target : a self-refining feedback system over the reference image channels, choosing work as slots free up, with a brake against overfocusing one category until the queue stacks up
- needed meanwhile as a tool : BATCH EDIT of queued items -- swap a reference image for a better version, apply newly found parameters to matching items, update segments of queued prompts. elfdb already plans DYNAMIC PROMPT TEMPLATES : the owner calls that the more durable and generic approach [ an item references a template, editing the template updates every item ]. owner : templates are STREAM EDITING -- a direction of change is judged desirable once, then applies to future, still unknown input with an expectable quality and style range tools help whichever construct they control ; transition may be gradual
- gallery needs scaling support for reference images, not doable today without redundancy -> N7FS references [ one node, many holders ] may be the base
- elfdb and similar design plans [ ~62 mentions under data/ ] may already cover part : review them and write a design note [ promised, "whenever convenient", after N7FS stage 3 ]
- continuity matters : owner keeps the GPU [ fan needs repair ] to keep things running ; azurum installed and N7FS prioritized to solve the distributed data islands problem for good ; jobsite zenka already moved off the GPU to the remote servers [ a milestone ]

**Why:** steers render tooling and N7FS priorities toward continuous operation and away from manual queue work.
**How to apply:** treat queue tools as interim helpers ; design toward the native loop ; check [[n7fs-current-state]] when storage is involved.
