`bin/todo` (2026-08-09, commits `4dde33fc2` and prior on the same session)
went through three id-scheme iterations before landing:

1. monotonic `next_id` counter, displayed raw (`5,6,7,9,12,13` — gappy,
   grows forever, deletions never free a slot).
2. monotonic id + a derived 3-char `chk` field (`amos_chksum` truncated to
   3 chars) for display only. Measured collision behavior: cumulative
   collision rate across *all-time issued* sequential ids saturates fast
   (4.6% by id 1000, 19% by 4200, 90% by 100k) because it's a fixed
   32,768-slot space — but collision among only the *currently open*
   items (the actually relevant risk) stays low even as the historical
   pool grows (0.07% at 5 open items, 2% at 20, ~12% at 50) since it's a
   birthday-paradox draw from a small live sample, not the full history.
3. **landed design**: dropped the id/chk split entirely. The id itself is
   directly random (not derived from any counter), generated by
   `gen_id()` mirroring `modules/base.gen_id`'s shape — random candidate,
   reject if it collides with any id currently present in the file,
   reject if it fails `AMOS7::Assert::Truth::is_true` (harmonic gate,
   measured ~99.6% pass rate so it costs almost nothing), retry up to 200
   times, falling back to skipping the harmony gate if that many retries
   fail. `base.gen_id` itself can't be called directly from `bin/todo`
   (or any standalone `bin/` script) — it's a zenka module using the
   `<[...]>` routing syntax and depends on `<base.prng.fortuna>`, a PRNG
   object living in a running zenka's `%data`, not available outside the
   zenka runtime; `rand()` substitutes for Fortuna in the standalone port.

**Why this is the right general shape for a short reusable display id**:
deriving a short code from a growing sequential source (option 2) hits
birthday-paradox saturation as the source range grows, even though the
derived code space itself doesn't grow. Generating the code directly and
checking it against only what's *currently in use* sidesteps that
entirely — the effective collision risk is always against the live set
size, not all-time issued count, and deleting an item frees its code
immediately (no renumbering, no permanent gaps) since collision-checking
only ever looks at what's still present in the file.

**How to apply**: if another part of the project ever wants a short,
reusable, human-typeable display id (not a permanent audit-trail id), this
generate-and-check-against-current-set pattern is the one to reach for,
not hash-of-a-growing-counter. See [[topic-addressing-trinity]] for the
project's broader checksum-addressing philosophy this sits inside, and
[[feedback-amos-chksum-listcontext-gotcha]] for a real bug hit while
implementing this.

Sort order in `bin/todo`'s listing also changed as a consequence: id is no
longer creation-ordered, so listing now sorts by item text using
`modules/base.sort`'s own two-pass algorithm (ascending length, ties
broken descending-alphabetical via a reverse-then-stable-sort) — the first
non-`base.sort`-internal reuse of that exact algorithm shape seen so far.
