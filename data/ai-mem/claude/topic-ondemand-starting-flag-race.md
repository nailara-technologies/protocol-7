**RESOLVED BY DESIGN, 2026-07-09, commit `056597b9b`:** rather than keep hunting the exact code path that deletes the session-route key (see "still unresolved" below — never found, six theories ruled out), the fix bounds the damage structurally so a lost reply can never wedge a zenka forever, regardless of cause:
- `base.handler.command.route_to_target` now starts a per-`v_id` watchdog timer (`starting_watchdog`, default 90s) alongside `starting=5`.
- New `base.zenki.ondemand.handler.reconcile_starting` fires on timeout: checks observable truth (`$data{user}{name}{session}`) — if actually online (the lost-reply race), re-fires `v7.notify_online` so the existing "already online" branch rescues/delivers the whole queue normally; if genuinely gone, fails the queue back with a real error and clears `starting`/`starting_since` so the next caller gets a real fresh-start attempt.
- Both existing reply handlers (`base.handler.ondemand_startup`, `base.zenki.ondemand.handler.startup_reply`) cancel the watchdog wherever they clear `starting` on the normal path.
- Separately, discovered along the way: `restart.disabled=1` on-demand zenki (like `task`) had **zero** tolerance for a startup `error` — `v7.handler.zenka_status` called `zenka.cmd.stop` immediately on the first failure, a completely different code path from the `startup-error-retries`/`retry-count` mechanism (which doesn't apply to restart-disabled zenki at all and defaults to unlimited). Added a new `ondemand-consecutive-failures` counter, reset on reaching `online`, with a default-3 (configurable via `restart.consecutive-failure-tolerance`) tolerance before the real give-up/stop fires — below threshold the already-scheduled `v7.init_restart_timer` now actually gets to run instead of being short-circuited.
- Noted but deferred (minor): the new module lives in the `base.*` namespace, so it landed in every zenka's `subroutine.white-list` on regen, not just cube's — fine for now, worth reconsidering placement in a later pass.
- Signing required taeki's passphrase (couldn't be done by Claude); taeki ran `sourcecode update-signatures` + version bump, confirmed clean after a backend restart, then this was committed.

**Live symptom that triggered this (present at time of investigation, now fixed going forward): `<zenki.virtual>{717373}` (task zenka) has `starting = 5` stuck permanently true and `queue` holding 11 silently-undelivered commands, since 2026-07-03 ~18:50. Every other on-demand zenka's `zenki.virtual.*.queue` is empty. This is what caused jobsite to stop assessing new job postings (27 accumulated unassessed) — `jobsite.dispatch.assessments`'s `$was_idle` gate never sees `jobsite.cycle` return to idle because the one `task.create` dispatch that should have completed the cycle never gets a reply, since `task` itself can never be restarted again (routed commands just pile into the dead queue, forever, silently, no error/log/timeout anywhere in that path).

**Confirmed root mechanism (proven via live log evidence, not theory):**
Cube's persisted log (`/var/log/protocol-7/DESKTOP-FP4OP26.DESKTOP-FP4OP26.cube.zenka.log` — note the doubled-hostname filename is the *active* one; the non-doubled `DESKTOP-FP4OP26.cube.zenka.log` is stale/rotated out, last written Jun 19) contains, at `17:50:03.699` on 2026-07-03 (converted via `p7c localtime <log-line-id>`):
```
[3750300] TRUE-reply to unknown route id [741070], ignored.
```
This is ~3ms after task's own `[initialized]` log line. `741070` is the `target.cmd_id` of route `2331104` — the stage-2 `v7.notify_online` poll route created by `base.handler.ondemand_startup` (self-addressed: `source.sid == target.sid == 3750300`, v7's own persistent session, per `base.protocol-7.command.send.local`'s universal pattern of setting `source.sid = target_sid` for all locally-originated commands). This proves: v7 genuinely finished resolving the deferred `notify_online` request and sent the correct `TRUE` reply back over its own session — but by the time cube's `base.handler.command.process_reply` parsed that incoming line, `$data{session}{3750300}{route}{741070}` was **already gone**, so it fell into the "unknown route id, ignored" branch instead of ever reaching `base.zenki.ondemand.handler.startup_reply` (the only code path that clears `starting`). Comparing to a structurally-identical, successful `powershell` on-demand start minutes later in the same log — identical 3-line startup sequence, but powershell's 4th line is the success log ("ondemand powershell zenka has come online..,") instead of the drop — confirms this is a genuine narrow timing race specific to that one occurrence, not a structural flaw in the self-addressed-route mechanism (which works fine every other time, including for every other on-demand zenka observed cycling in the same multi-hour window).

**Still unresolved:** the exact code path that deletes (or never writes) session-route key `741070` in that ~3ms window. Ruled out candidates delete *more* than just that one key (see below), but the observed signature — `source.cmd_id` key `7171991` still present and correctly pointing to the still-open global route `2331104`, target key `741070` alone missing, global route object never deleted — requires something that deletes *only* the target-side session-route key. `base.cmd.cancel-stream` is the only code found with that exact narrow deletion shape, but no matching "cancel-stream cmd_id=..." log line or `stream_cancelled` entry for `741070`/`7171991` exists, so it's unconfirmed, not proven.

**Theories investigated and ruled out (do not re-litigate without new evidence):**
1. Self-addressed route (source.sid==target.sid) is inherently fragile — false; universal pattern for all `send.local` calls, confirmed safe under repeated real-world cycling of every other on-demand zenka.
2. Duplicate v7 session causing a double self-addressed poll — impossible; losing v7's cube connection restarts cube itself, and `v7.callback.connect_to_cube` recreates the sole connection to the new cube instance. Confirmed by the zenka's owner.
3. Cross-namespace `gen_id` collision between `send.local`'s global-route-table-checked `$cmd_id` and `route.add`'s session-hash-checked `$target_cmd_id` — rejected by the zenka's owner: `base.gen_id`'s collision loop correctly avoids collisions against whichever hash it's given; invoking coincidental cross-hash collision to explain one incident, against a mechanism exercised cleanly tens of thousands of times, isn't well-founded without direct evidence.
4. STRM `stream_cancelled` markers / `!TERM!` cancellation — unrelated; confirmed a separate, already-understood, currently-harmless cleanup gap (STRM producer terminated mid-stream leaves session-side route entries dangling after already-deleted global routes). `741070`/`7171991` were never part of any STRM interaction and don't appear in `stream_cancelled`.
5. Oversized single-line command wedging the session input buffer (`size.buffer.input = 242707` bytes in `configuration/shared-params`; P7's plain TRUE/FALSE/WAIT/command wire path has no length-prefix framing — confirmed via [[feedback-oversize-single-line-protocol]] and by reading `base.handler.command`'s incomplete-line fallback, which waits forever with no drop/timeout) — real and separately worth tracking, but empirically ruled out as *this* bug's cause: tested live against a cold `powershell` zenka with a raw 304KB single-line command (bypassing `p7c`'s argv-size shell limits via a small custom socket script replicating its auth handshake) — no reply ever came back, but `zenki.virtual` for that zenka was *never touched at all* (routing never even got attempted). Task's case proves routing/dispatch *did* succeed and the zenka *did* come fully online — the failure is later, in reply delivery, not in initial command parsing. Different failure point.
6. `v7.handler.zenka_status`'s "send set-initialized before notify_online replies" step creating a second, interfering route on session 3750300 at the critical moment — ruled out on two counts: (a) the comment's actual purpose is unrelated to reply-delivery races — it's about letting a zenka's own startup contact its dependencies and only then decide to come online/fail, so other zenki depending on it can trust the `initialized` flag; (b) mechanically, `$instance->{'root_sid'}` is **not** v7's own cube session id — it's whatever session id *that specific instance* (task) was assigned by cube via its own `whoami` call during its own startup (i.e. task's `cube_sid`, `4035090`), exactly analogous to how v7 itself learned `3750300` for its own connection long ago. So `"$root_sid.set-initialized"` session-ID-routes to task's own session (`4035090`), a completely different route hash from `$data{session}{3750300}{route}` where the stuck key `741070` actually lives — never touches it.

**Diagnostic technique notes for next time:**
- `p7c` (or `::`) can run direct read-only diagnostic commands against the live system: `dump <path>`, `v7.dump <name>`, `list sessions [name]`, `eval-code <perl>` (devmod), `localtime <log-line-id>` to convert a log entry's leading id to a real timestamp.
- `p7c`'s CLI hits the shell's own argv-size limit (`Argument list too long`) well under 150-300KB in this environment — to send an oversized payload for testing, write it to a file and use a small custom script that replicates `p7c.c`'s handshake (`select unix` / `auth unix-<user>` / `select-strm-mode locked`) over the raw unix socket directly, rather than shelling out through `p7c`'s argv.
- The live, actively-written cube log has a doubled-hostname filename (`DESKTOP-FP4OP26.DESKTOP-FP4OP26.cube.zenka.log`); the non-doubled name is a stale/rotated file, not the active log — check `ls -la` timestamps before trusting which one is current.
- Cross-referencing a failed sequence against a structurally-identical *successful* sequence for a different zenka, in the same log, is what actually pinned down "this is a real race, not a structural flaw" — worth doing early next time rather than pure static code reading.

**Status as of 2026-07-04:** investigation paused here — every mechanism constructed from reading the code (6 distinct theories) was ruled out on solid grounds, including one dispatched to Kimi and one to Claude Opus independently, both converging on the same dead ends without finding the exact deleting line. The confirmed fact (real race: reply arrived, route already gone, proven via live log) stands; the precise trigger does not. The zenka's owner's conclusion at this point: this level of narrow, hard-to-pin-down races in the on-demand start/route/reply layer points toward a complete refactor of that subsystem being the actual solution, rather than continuing to hunt for a single-line fix. Task's live stuck state (`zenki.virtual.717373`) was deliberately left untouched throughout this entire investigation and is presumably still stuck as of this writing.
