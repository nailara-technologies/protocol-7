**the model [ user ]** : entities share one model -- a key-anchored branch
in the dot namespace, sessions, grants, a current node -- and differ only
in what drives them.

1. zenki [ code ]
2. users [ people ]
3. llms [ as zenki, or by themselves ]
4. the network [ expected to join as an entity of its own ]
5. instantiations by the network [ could be a type of their own already ]

- **sub-branching is native for every type** : any branch can hold
  further branches [ `usr.taeki.cfg.hosts..`, a zenka's own
  `<branch>.cfg..` ] with the same prefix stripping, current node and
  owner key over everything below
- already true in small : zenki authenticate to cube as sessions with keys
  like users, share `access.cmd.usr.<name>` grants, links carry
  `link_user` labels -- grant \ trust code never needed two versions

**How to apply:** new identity, access or config work gets ONE code path
for all entity types ; a special case for 'zenka vs user' is a sign the
model is missing a piece. see [[vision-2026-10-28-declared-intent-survives-breakage]],
data/md/design/HOST-SETUP.md 'records', project-vision-origin [ network as
primary entity ].
